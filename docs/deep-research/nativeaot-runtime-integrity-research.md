# NativeAOT User-Mode Runtime Integrity on Windows 11

## 1. Introduction to User-Mode Process Hardening and the Zero-Trust Architecture

The architectural landscape of modern Windows 11 system configuration utilities demands highly stringent security boundaries, particularly when operations bridge user-mode graphical interfaces and highly privileged Session 0 kernel-adjacent services. The ThisIsMyPC application embodies this paradigm, relying on a WinUI 3 graphical client, a Session 0 Windows Service, and the PawnIO.sys third-party kernel driver for direct hardware access. While kernel-side protections such as ObRegisterCallbacks, CmRegisterCallbackEx, and minifilter persistence establish a formidable barrier against unauthorized handle acquisition and file tampering, the user-mode execution space remains a prime target for exploitation. Attack vectors such as memory corruption, return-oriented programming (ROP), and arbitrary dynamic-link library (DLL) injection can circumvent kernel defenses by hijacking trusted user-mode processes to execute privileged commands.

To neutralize these threats, applications must leverage advanced Windows 11 exploit mitigations, specifically Control Flow Guard (CFG), Arbitrary Code Guard (ACG), and Code Integrity Guard (CIG). The adoption of .NET 10 NativeAOT (Ahead-of-Time) compilation for single-file executables fundamentally alters how these mitigations interact with the application. By compiling Intermediate Language (IL) directly to native machine code at publish time, NativeAOT eliminates the Just-In-Time (JIT) compiler, inadvertently aligning the application with the strictest executable space protection policies.[^1]

This research report provides an exhaustive technical analysis of deploying CFG, ACG, and CIG within a .NET 10 NativeAOT and WinUI 3 environment. It investigates compatibility constraints, optimal initialization timing, dependency management, the preservation of interop metadata via CsWin32, and the strategic integration of Windows Defender Application Control (WDAC) to achieve a zero-trust user-mode runtime.

## 2. Control Flow Guard (CFG) in the .NET 10 NativeAOT Pipeline

Control Flow Guard (CFG) is a highly optimized platform security feature introduced to combat memory corruption vulnerabilities by placing tight restrictions on where an application can execute code from.[^1] By validating indirect call targets against a pre-computed bitmap before execution, CFG severely restricts an attacker's ability to exploit buffer overflows via arbitrary code execution or Return-Oriented Programming (ROP) chains.[^1]

### 2.1. NativeAOT Support and MSBuild Configuration

The .NET 10 NativeAOT compilation pipeline fully supports Control Flow Guard; however, it is not enabled by default due to a minor increase in compilation time and final binary size.[^5] The NativeAOT compiler (ILCompiler) acts as a front-end that generates native object files, which are then passed to the platform-specific linker (e.g., link.exe on Windows).[^7]

To enable CFG, developers must explicitly modify the project's MSBuild configuration. Unlike traditional C++ projects where `/guard:cf` is passed directly to the compiler and linker, NativeAOT provides a managed abstraction via the `.csproj` file. This property instructs the underlying Microsoft Visual C++ (MSVC) linker to instrument the binary with the necessary validation routines.[^1]

The following table details the necessary MSBuild properties required to harden a .NET 10 NativeAOT application:

| MSBuild Property | Value | Purpose | Reference |
|---|---|---|---|
| `PublishAot` | `true` | Enables NativeAOT compilation during the publish phase, eliminating the JIT compiler and producing a standalone native binary. | [^1] |
| `ControlFlowGuard` | `Guard` | Instructs the AOT compiler and the native linker to emit CFG checks for indirect calls and generate the Guard CF Function Table (GFIDS). | [^1] |
| `CetCompat` | `true` (Default) | Enables Control-flow Enforcement Technology (CET) Shadow Stack, providing hardware-backed ROP mitigation alongside CFG. | [^1] |
| `IlcGenerateMstatFile` | `true` | Optional. Generates a map file useful for auditing the emitted native code and ensuring proper CFG bitmap alignment. | [^7] |

When `<ControlFlowGuard>Guard</ControlFlowGuard>` is defined, the .NET build system automatically appends the required `/guard:cf` flags.[^1] Verification of the compiled executable can be performed using the `dumpbin /headers /loadconfig <binary.exe>` command, which will expose the presence of the `CF Instrumented` and `FID table present` flags within the Portable Executable (PE) header.[^1]

### 2.2. Compatibility with AOT Indirect Call Patterns

A critical consideration for the implementation of Control Flow Guard is its compatibility with the complex indirect call patterns generated by the .NET runtime. In a managed environment, virtual method dispatch, delegate invocations, interface calls, and interface dispatch stubs rely heavily on indirect jumps, which are the exact mechanisms CFG is designed to monitor.

The NativeAOT runtime, powered by the RyuJIT compiler during the pre-compilation phase, has been extensively engineered to support CFG natively.[^6] Whenever RyuJIT encounters an indirect method call, it transforms the machine code to interact with the OS-provided CFG validation helpers. For example, on x64 architectures, the destination address is placed in the RAX or RCX register, and control is passed to `LdrpDispatchUserCallTarget` or `LdrpValidateUserCallTarget`.[^6]

The NativeAOT compiler accurately enumerates all valid function pointers and address-taken methods during the build phase, populating the Guard CF Function Table (GFIDS table) in the PE load configuration directory.[^9] Consequently, there are no known compatibility issues where CFG misclassifies legitimate NativeAOT indirect calls. The compiler guarantees that all valid entry points are accurately registered in the CFGBitmap, preventing false-positive process terminations that plagued early iterations of managed CFG implementations.[^4]

### 2.3. CsWin32 P/Invoke Interop and Metadata Preservation

The ThisIsMyPC application relies on CsWin32, a Roslyn-based source generator, to project Win32 APIs and COM interfaces into C# without the overhead of manual declarations.[^11] A primary architectural concern is whether CsWin32-generated code correctly preserves CFG metadata, specifically when transitioning across the managed-to-unmanaged boundary via P/Invoke or when handling unmanaged callbacks.

CsWin32 operates entirely at compile time, meaning its output is ingested directly into the NativeAOT pipeline.[^12] For optimal NativeAOT compatibility, CsWin32 must be configured to avoid the built-in .NET runtime marshaler, which is historically reliant on dynamic code generation to build interop thunks. This configuration is achieved via a `NativeMethods.json` file placed in the project root:

```json
{
  "$schema": "https://aka.ms/CsWin32.schema.json",
  "allowMarshaling": false
}
```

By explicitly setting `"allowMarshaling": false`, CsWin32 is forced to generate unmanaged function pointers and utilize the `LibraryImport` attribute alongside the `ComWrappers` API, completely avoiding the legacy `DllImport` marshaler.[^14] Because these artifacts are generated prior to the AOT compilation phase, the NativeAOT compiler can statically analyze all interop boundaries. The ILCompiler successfully identifies these static function boundaries and emits their relative virtual addresses (RVAs) into the CFG GFIDS table.[^7]

For callbacks originating from native code — such as the PawnIO.sys kernel driver sending hardware interrupts back to user-mode via function pointers — NativeAOT utilizes the `[UnmanagedCallersOnly]` attribute.[^16] The compiler inherently tags any method marked with `[UnmanagedCallersOnly]` as a valid address-taken target. This ensures that when the Windows kernel or a native DLL invokes the callback, the target address is already present in the CFG bitmap, and validation succeeds seamlessly.[^9]

## 3. Arbitrary Code Guard (ACG) and Dynamic Code Restrictions

Arbitrary Code Guard (ACG), programmatically enforced via the `ProcessDynamicCodePolicy`, represents a paradigm shift in Windows user-mode security by enforcing the W^X (Write XOR Execute) memory protection policy. When active, the Windows memory manager strictly prohibits the allocation of virtual memory pages with `PAGE_EXECUTE_READWRITE` permissions and blocks the modification of existing executable pages (e.g., preventing `VirtualProtect` from altering a code segment to become writable).[^17] This permanently closes a fundamental exploitation primitive: the injection and execution of malicious shellcode into data segments or over existing executable code.[^17]

### 3.1. Safety and Enablement in NativeAOT

Traditionally, managed .NET applications are entirely incompatible with Arbitrary Code Guard. The Just-In-Time (JIT) compiler fundamentally relies on dynamically generating, writing, and mapping executable memory pages at runtime to translate IL into machine code.[^19] Enabling ACG on a standard CoreCLR application results in an immediate crash as the JIT compiler is denied the ability to allocate executable memory.

However, .NET 10 NativeAOT resolves this limitation natively. Because the application is compiled to native machine code prior to execution, the requirement for dynamic IL-to-native translation is eradicated.[^1] NativeAOT processes do not rely on `VirtualAlloc` for code execution.[^1]

The following table analyzes the compatibility of internal runtime components with ACG:

| NativeAOT Component | ACG Compatibility | Technical Justification | Reference |
|---|---|---|---|
| **Garbage Collector (GC)** | Compatible | The NativeAOT GC (derived from CoreCLR) manages memory strictly within data segments (`PAGE_READWRITE`). It does not emit or require executable instructions to function. | [^7] |
| **Exception Handling (EH)** | Compatible | Exception unwinding in NativeAOT has been rewritten to rely on static native unwinding data (DWARF or Windows SEH) generated at compile time, completely abandoning dynamically generated EH funclets. | [^22] |
| **Interop Thunks** | Compatible | By utilizing `LibraryImport` and `[UnmanagedCallersOnly]`, all interop thunks are emitted statically at compile-time. There is no runtime generation of IL stubs for P/Invoke operations. | [^1] |
| **Reflection** | Partially Compatible | Bounded reflection (analyzable at compile time) is supported. Unbounded reflection (`Type.MakeGenericType`, `Reflection.Emit`) is disabled and will throw exceptions, preventing dynamic code execution. | [^1] |

As long as the ThisIsMyPC codebase strictly adheres to NativeAOT trimming constraints — specifically avoiding `System.Reflection.Emit` and unbounded generic instantiations — the `ProcessDynamicCodePolicy` can be safely and effectively enabled without inducing runtime crashes.[^24]

### 3.2. WinUI 3, Windows App SDK, and Dynamic Code Conflicts

Integrating WinUI 3 (delivered via the Windows App SDK) into an ACG-enforced process introduces significant architectural considerations. WinUI 3 is heavily reliant on XAML parsing, data binding, and COM interop, which historically utilized dynamic code generation.[^26]

1. **XAML Initialization and Data Binding**: Unbounded reflection for XAML data binding will fail under both NativeAOT and ACG. WinUI 3 applications compiled with NativeAOT must utilize compiled bindings (`{x:Bind}` instead of `{Binding}`) and ensure all XAML views are AOT-compiled.[^26] As of Windows App SDK 1.6, substantial improvements have been integrated to support NativeAOT, bypassing legacy reflection-heavy code paths that would otherwise violate ACG.[^28]

2. **WebView2 (Chromium Engine)**: If the ThisIsMyPC GUI utilizes WebView2 to render specific dashboard elements, ACG presents a distinct challenge. Modern browser engines require JIT compilers (e.g., the V8 JavaScript engine) to execute JavaScript performantly. To reconcile this, Microsoft engineered WebView2 to isolate its JIT functionality into an external, sandboxed child process.[^19] This out-of-process architecture ensures that the main WinUI 3 host process can maintain strict ACG enforcement while delegating dynamic code generation to the severely restricted WebView2 rendering utility.

3. **Bootstrapper Limitations**: Unpackaged WinUI 3 apps utilize a Bootstrapper API (`Microsoft.WindowsAppRuntime.Bootstrap.dll`) to dynamically locate and load the Windows App SDK framework packages at runtime.[^30] While the Bootstrapper itself utilizes standard `LoadLibrary` calls and does not generate dynamic code, its reliance on loading external DLLs necessitates careful timing regarding when ACG and CIG are enforced.

### 3.3. Execution Timing: When to Apply Process Mitigations

The initialization sequence and the timing of enabling Arbitrary Code Guard are paramount to the application's overall security posture. Calling the `SetProcessMitigationPolicy` API programmatically via `kernel32.dll` at the beginning of the `Main()` method is frequently recommended in generalized documentation.[^18] However, for a high-security tool like ThisIsMyPC, this approach leaves a critical vulnerability window.

When the OS loader (`ntdll.dll`) initializes a process, it resolves the Import Address Table (IAT) and executes the `DllMain` functions of all statically linked dependencies *before* control is handed to the application's managed `Main()` entry point.[^31] If an attacker leverages a persistence mechanism (such as the `AppInit_DLLs` registry key, or DLL search order hijacking) to inject a payload, that malicious code will execute in a completely unprotected, non-ACG environment prior to the mitigation being toggled by the application code.

To completely seal this window, `ProcessDynamicCodePolicy` must be enforced *before* the process is initialized. This cannot be achieved programmatically within the process itself. It must be achieved via process creation attributes (`PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY` from a trusted launcher) or through operating system configurations such as Image File Execution Options (IFEO).[^31]

## 4. Code Integrity Guard (CIG) and Dependency Loading

Code Integrity Guard (CIG), enforced via the `ProcessSignaturePolicy`, ensures that the Windows Memory Manager will only map executable pages that contain a cryptographic signature verifying Microsoft, Windows Store, or Windows Hardware Quality Labs (WHQL) provenance.[^34] Any attempt to map an unsigned, improperly signed, or maliciously altered DLL results in the memory manager throwing a `STATUS_INVALID_IMAGE_HASH` exception, abruptly terminating the load sequence.[^34]

### 4.1. CIG Compatibility with NativeAOT and WinUI 3

Enabling CIG on a NativeAOT application is inherently elegant. Because NativeAOT compiles the entire .NET runtime, the garbage collector, and all managed third-party NuGet dependencies into a single, unified native binary, the traditional reliance on mapping dozens of managed `.dll` files is eliminated.[^2]

If the ThisIsMyPC executable is digitally signed with an appropriate Extended Validation (EV) certificate, the entire application logic inherently passes CIG enforcement. Furthermore, WinUI 3's underlying native components (`Microsoft.ui.xaml.dll`, `dwrite.dll`, `mrtcore.dll`) are signed by Microsoft, ensuring they load seamlessly under Microsoft-only or Microsoft+Store CIG policies.[^35]

### 4.2. Impact on Third-Party DLL Injections

When CIG is active, the process becomes actively hostile to external software attempting to inject libraries.

- **Benign Interference**: Legitimate third-party software, such as GPU overlay drivers (e.g., RivaTuner, NVIDIA overlays), antivirus hooks, or unofficial accessibility tools, frequently inject unsigned or non-WHQL signed DLLs into user-mode processes.[^19] Under CIG, these injections will silently fail. While this dramatically improves security, it may cause user-end diagnostic errors or cause overlay software to fail.
- **Malicious Interference**: Attackers attempting classic DLL injection, reflective DLL injection, or shellcode execution via `LoadLibrary` will be categorically blocked by the kernel's memory manager before the payload ever enters the address space.[^17] The attack surface associated with malicious modules is entirely negated.

### 4.3. Allowlisting Specific Unsigned DLLs

A core architectural challenge arises if ThisIsMyPC must intentionally load a third-party unsigned DLL (for instance, an open-source hardware telemetry library or a proprietary peripheral driver companion DLL). The `SetProcessMitigationPolicy` API is binary; it does not support passing an array of allowed exceptions or custom certificates.[^38]

To overcome this, the architecture must pivot from legacy API calls to Windows Defender Application Control (WDAC). WDAC allows administrators to define highly granular Code Integrity (CI) policies that apply natively to the kernel's memory manager, effectively acting as an advanced, customizable version of CIG.[^39]

Using WDAC Supplemental Policies, ThisIsMyPC can enforce strict CIG on the process while explicitly allowlisting an unsigned DLL by its cryptographic hash or file path. This is achieved by generating a WDAC XML policy[^39]:

```xml
<FileRules>
  <Allow ID="ID_ALLOW_UNSIGNED_DLL" FriendlyName="LegacyTelemetry.dll" Hash="" />
</FileRules>
```

By deploying this policy (either merged into a Base Policy or as a Supplemental Policy) via the `New-CIPolicy` and `ConvertFrom-CIPolicy` PowerShell cmdlets, the OS memory manager will honor CIG for all unknown binaries but permit the explicitly hashed DLL to map into the process.[^39]

## 5. Interaction with Kernel Protections and the Attack Surface

The security architecture of ThisIsMyPC relies on a defense-in-depth model. The kernel driver, PawnIO.sys, utilizes `ObRegisterCallbacks` to strip `PROCESS_VM_WRITE`, `PROCESS_VM_READ`, and `PROCESS_CREATE_THREAD` access rights from handles requested by untrusted processes. This effectively isolates the GUI and Session 0 service from traditional out-of-process memory tampering, such as credential dumping or external shellcode injection.

### 5.1. The "Already In-Process" Attack Surface

If a sophisticated adversary bypasses `ObRegisterCallbacks` — perhaps via an exploited vulnerable driver in a Bring Your Own Vulnerable Driver (BYOVD) attack, or by achieving code execution *before* the application fully initializes and secures its handle — the threat model shifts entirely to the in-process mitigations.[^17]

Assuming the attacker successfully bypasses kernel isolation and injects a payload into the WinUI 3 process, the interplay of ACG and CFG severely restricts their capabilities:

1. **Immutability of Code**: Because ACG (`ProcessDynamicCodePolicy`) is active, the attacker's injected code cannot call `VirtualAlloc` to allocate a new RWX memory region for stage-two payloads or shellcode.[^18]
2. **Protection of Existing Code**: The attacker cannot call `VirtualProtect` to overwrite the existing `.text` section of the NativeAOT binary to establish inline hooks or disable internal security checks.[^17]
3. **Restriction to ROP/JOP**: Stripped of the ability to execute new arbitrary code, the attacker is forced to rely on Return-Oriented Programming (ROP) or Jump-Oriented Programming (JOP) by chaining together existing executable instructions (gadgets) found within the NativeAOT binary or loaded system DLLs.[^18]
4. **CFG Mitigation**: This is where Control Flow Guard provides critical defense. As the attacker attempts to manipulate function pointers (e.g., hijacking a delegate, a WinUI 3 callback, or a COM virtual table) to redirect execution flow toward their ROP chain, the CFG bitmap validation will detect that the target address is not a valid function entry point.[^6] The OS will immediately terminate the process (`STATUS_STACK_BUFFER_OVERRUN`), neutralizing the attack.

### 5.2. Timing and Enforcement Mechanisms: Manifest vs. IFEO

As established, programmatic enablement of mitigations via `SetProcessMitigationPolicy` is vulnerable to Time-of-Check to Time-of-Use (TOCTOU) logic flaws during process initialization.[^31] To ensure absolute runtime integrity, mitigations must be enforced by the OS loader before `ntdll.dll` maps dependencies.

The following table compares the viability of various enforcement mechanisms:

| Mitigation Method | Timing of Enforcement | Suitability for High-Security Deployments | Technical Limitations | Reference |
|---|---|---|---|---|
| `SetProcessMitigationPolicy` (API) | Post-initialization (`Main()`) | Low | Vulnerable to early DLL injection, static import hijacking, and `DllMain` exploitation. | [^31] |
| `UpdateProcThreadAttribute` Process Creation (Launcher) | Medium | Medium | Requires a secure, secondary launcher process to spawn the target application. | [^19] |
| PE / Appx Manifest | Pre-initialization | High | Native integrations for UAC/DPI, but lacks explicit XML schema support for granular ACG/CIG enforcement. | [^43] |
| IFEO Registry Keys | Pre-initialization | Optimal | Applied natively by the OS loader before the first instruction executes. Modifies `MitigationOptions`. | [^17] |
| WDAC (App Control) | OS-Level Enforcement | Optimal | Deep kernel/hypervisor integration. Cannot be bypassed by user-mode administrators without rebooting. | [^39] |

While the PE Application Manifest (`app.manifest` or `appxmanifest.xml` for MSIX packaged WinUI apps) is ideal for enforcing UAC elevation (`requestedExecutionLevel`) and OS compatibility boundaries, it lacks direct XML schema support for declaring Arbitrary Code Guard (`ProcessDynamicCodePolicy`) and Code Integrity Guard (`ProcessSignaturePolicy`).[^43]

Therefore, for the ThisIsMyPC Session 0 service and GUI, the most robust architectural deployment involves configuring **Image File Execution Options (IFEO)** during installation. By writing to `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\ThisIsMyPC.exe` and setting the `MitigationOptions` QWORD, the OS memory manager (`ntdll!LdrLoadDll`) enforces ACG and CIG atomically during process birth.[^17]

## 6. Practical Deployment and Performance Analytics

Transitioning these mitigations from a theoretical concept to a stable commercial deployment requires an understanding of the broader ecosystem, the performance cost, and the ongoing management overhead.

### 6.1. Commercial Feasibility and Production Precedents

Deploying NativeAOT, CFG, ACG, and CIG in tandem on Windows 11 is highly viable and is currently utilized by flagship Microsoft products. Components of the Windows OS, the Microsoft Edge browser (which isolates rendering processes with strict ACG/CIG bounds to prevent browser-based RCE), and the recently released Aspire CLI are compiled and hardened using identical paradigms.[^19] Furthermore, the Windows Community Toolkit explicitly supports NativeAOT, proving that complex, high-performance UI components can be rendered without runtime code generation.[^46]

### 6.2. Performance Overhead on NativeAOT and WinUI 3

Combining NativeAOT with aggressive OS mitigations yields a highly secure but uniquely performant profile, often outperforming equivalent JIT-compiled software.

- **NativeAOT Base Performance**: The shift to NativeAOT inherently reduces the application's disk footprint (often dropping below 15MB for self-contained UI apps), drastically limits memory allocation demands, and accelerates cold-start times (up to a 70-80% reduction compared to JIT compilation).[^2]
- **CFG Overhead**: The compiler analysis isolates checks strictly to indirect jumps. At runtime, the Windows kernel's highly optimized CFG bitmap lookup introduces a fractional microsecond delay per indirect call.[^48] Given that NativeAOT aggressively inlines methods and resolves dependencies statically at compile time, the overall frequency of indirect calls is lower than in heavily abstracted JIT frameworks. The overall CPU overhead on a WinUI 3 application is generally below 1-2%, which is imperceptible to the end user.[^49]
- **ACG Overhead**: Arbitrary Code Guard has **zero execution-time overhead**.[^17] Because ACG is enforced at the memory page allocation level, it only invokes logic when `VirtualAlloc` or `VirtualProtect` are called. Since a NativeAOT app does not dynamically allocate executable memory during its lifecycle, these checks are never continuously triggered during normal software execution.[^1]
- **CIG Overhead**: Code Integrity Guard impacts performance exclusively during module loading.[^34] The OS calculates the cryptographic hash of a DLL and validates its signature chain against the trusted root. Because NativeAOT bundles the vast majority of the application into a single executable, the number of individually loaded modules is drastically reduced, effectively mitigating the I/O and CPU cost of signature validation at startup.[^47]

### 6.3. WDAC as the Ultimate Fallback

Relying strictly on IFEO registry keys or application-level API calls can be administratively fragile, as local administrators or competing software installers can inadvertently overwrite the registry state, potentially disabling the mitigations.

To ensure continuous compliance in enterprise or hardened environments, **Windows Defender Application Control (WDAC)** serves as the ultimate fallback and primary enforcer.[^39] WDAC policies are compiled into binary `.cip` files, loaded into the EFI partition, and enforced directly by the hypervisor via Hypervisor-Protected Code Integrity (HVCI).[^40] By deploying a WDAC base policy that mandates Unsigned System Integrity restrictions and dynamic code prohibitions, ThisIsMyPC can guarantee that its binaries — and only its explicitly allowlisted dependencies — are executed, rendering user-mode bypasses mathematically infeasible.[^40]

## 7. Synthesis and Strategic Recommendations

The integration of .NET 10 NativeAOT with Windows 11 user-mode exploit mitigations creates an exceptionally hostile environment for threat actors. By removing the JIT compiler, NativeAOT transforms the managed code landscape into a static, highly predictable execution graph that aligns perfectly with strict security policies.

To achieve maximum runtime integrity for the ThisIsMyPC WinUI 3 GUI and Session 0 service, the following architectural steps are strictly recommended:

1. **MSBuild Enforcement**: Configure both the GUI and Service `.csproj` files with `<PublishAot>true</PublishAot>` and `<ControlFlowGuard>Guard</ControlFlowGuard>`. This ensures the MSVC linker emits the necessary GFIDS tables for CFG validation.
2. **Interop Modernization**: Maintain the `NativeMethods.json` configuration for CsWin32 with `"allowMarshaling": false`. This forces the generation of AOT-compatible `LibraryImport` and `ComWrappers` interop code, allowing the ILCompiler to accurately map unmanaged boundaries into the CFG bitmap without relying on dynamic IL thunks.
3. **Pre-Initialization Policy Application**: Abandon the use of `SetProcessMitigationPolicy` within the application's runtime logic. Instead, utilize the software installer to configure Image File Execution Options (IFEO) in the Windows Registry, enabling `ProcessDynamicCodePolicy` (ACG) and `ProcessSignaturePolicy` (CIG) before the OS loader executes `DllMain` functions.
4. **WDAC Supplemental Allowlisting**: For any required unsigned third-party dynamic libraries, generate a WDAC Supplemental Policy (`New-CIPolicy`) utilizing the SHA-256 hash of the target DLL. Deploy this policy alongside the application to satisfy CIG requirements without breaking necessary external dependencies.

By layering kernel-mode handle isolation (ObRegisterCallbacks) with strict user-mode immutability (ACG), cryptographic verification (CIG), and control-flow integrity (CFG), the attack surface of ThisIsMyPC is reduced to a theoretical minimum. Even in the event of an arbitrary read/write primitive being discovered, the absence of executable space and the rigid validation of indirect calls render the execution of malicious payloads virtually impossible.
