# Core Component Threat Modeling and Security Architecture Analysis for ThisIsMyPC

## 1. Introduction and Architectural Context

The contemporary Windows 11 kernel architecture represents a highly restrictive, hypervisor-backed paradigm explicitly engineered to neutralize the fundamental assumptions of legacy malware, kernel-mode rootkits, and unauthorized hardware manipulation utilities. Historically, the Windows operating system treated execution within Ring 0 (kernel mode) as an absolute, unmitigated trust boundary. Any driver successfully mapped into kernel space possessed unfettered, pervasive access to physical memory, arbitrary hardware peripheral ports, and process execution states.^1^ However, the proliferation of Advanced Persistent Threats (APTs) and the industrialization of "Bring Your Own Vulnerable Driver" (BYOVD) attacks forced a systemic and philosophical evolution within Microsoft's security architecture.^1^ Modern Windows environments now deploy Virtualization-Based Security (VBS) and Hypervisor-Protected Code Integrity (HVCI), utilizing hardware-assisted virtualization technologies such as Second Level Address Translation (SLAT) and Extended Page Tables (EPT) to fundamentally alter the hierarchy of trust.^1^ Under this modern architecture, the hypervisor operates in an isolated environment known as Ring -1 (or Virtual Trust Level 1), acting as the ultimate arbiter of execution privileges over the primary operating system running in Virtual Trust Level 0 (VTL 0).^1^ This architecture enforces strict Write-XOR-Execute (W^X) protections, ensuring that kernel drivers can no longer assume the ability to map arbitrary executable memory or execute unconstrained IN/OUT port assembly instructions without triggering immediate hypervisor interceptions and catastrophic system halts.^1^

Within this highly constrained and heavily scrutinized ecosystem operates ThisIsMyPC, an open-source, GPLv2-licensed system configuration and hardware control utility. The primary operational directive of this tool is to persist user preferences against aggressive, automated operating system updates, feature rollouts, and Web Experience Pack modifications, while simultaneously providing low-level hardware control for features such as fan curves and RGB lighting arrays.^1^ The architecture of ThisIsMyPC spans three distinct privilege boundaries, necessitating a complex Inter-Process Communication (IPC) model. The user-facing component consists of a Graphical User Interface (GUI) executing as a medium-integrity desktop application in Session 1, requiring User Account Control (UAC) elevation for direct registry modifications. The persistence enforcement mechanism is decoupled into a background service operating as NT AUTHORITY\SYSTEM within Session 0, ensuring continuous telemetry and state enforcement regardless of the interactive user's presence.^1^ The hardware control and deepest state-enforcement capabilities are delegated to an Attestation-signed Windows Driver Framework (WDF) kernel module operating in Ring 0.^1^ This driver utilizes a custom PawnPP bytecode interpreter running within the PawnIO framework to execute hardware instructions safely, leveraging Advanced Configuration and Power Interface (ACPI) method invocations rather than raw port polling.^1^ Furthermore, the driver registers native Windows kernel callbacks, specifically CmRegisterCallbackEx and potentially FltRegisterFilter, to shield the user's configuration state from unauthorized alteration.^1^

The trust model of ThisIsMyPC introduces two distinct operational tiers: a default Admin Mode, which restricts functionality to user-mode registry tweaks without loading the persistent service or kernel driver, and an explicitly enabled Owner Mode, which instantiates the full architectural stack, including the Ring 0 driver and the Session 0 SYSTEM service.^1^ This multi-tiered, cross-boundary architecture presents a massive and highly complex attack surface. If an adversary manages to subvert the IPC mechanisms bridging the unprivileged GUI and the SYSTEM service, weaponize the bytecode interpreter inside the kernel driver, or hijack the state-enforcement callbacks, the tool designed to protect the system can be inverted into an impenetrable rootkit. This comprehensive research report rigorously deconstructs the documented attack patterns against architecturally similar software components. By actively researching vulnerabilities in comparable hardware control suites, analyzing the mechanics of named pipe impersonation, exploring IOCTL dispatch subversions, and evaluating the weaponization of kernel callbacks by advanced threat actors, this analysis formulates precise, industry-validated architectural mitigations. The objective is to ensure that the deployment of ThisIsMyPC does not inadvertently introduce catastrophic privilege escalation primitives or persistence shielding mechanisms into the modern Windows 11 kernel environment.

## 2. Threat Modeling: Initial Access Vectors and Component Vulnerability Profiling

A robust threat model must enumerate the specific attack paths available to an adversary based on their initial level of access to the target system. For ThisIsMyPC, the attack surface varies dramatically depending on whether the adversary operates as an unprivileged standard user, an elevated local administrator, or possesses local physical access to the hardware. Each architectural component -- the GUI, the Session 0 service, the kernel driver, and the update mechanism -- exhibits distinct vulnerabilities when subjected to these differing threat origins.

When an adversary possesses only unprivileged standard user access, the primary objective is Local Privilege Escalation (LPE) to achieve SYSTEM-level execution. In this scenario, the Session 1 GUI and its IPC channels to the Session 0 service are the primary targets. Unprivileged attackers routinely hunt for Time-of-Check to Time-of-Use (TOCTOU) race conditions, improper directory permissions, and insecure named pipe implementations.^3^ If the Session 0 service implicitly trusts requests originating from the GUI based solely on easily spoofed metadata such as Process IDs (PIDs) or user-space file paths, an unprivileged attacker can manipulate these data points to force the SYSTEM service to execute arbitrary code.^4^

If the adversary has already achieved elevated administrative privileges, their objective shifts from LPE to defense evasion, kernel-level persistence, and bypassing Hypervisor-Protected Code Integrity (HVCI). Operating as an administrator, the attacker can interact directly with the ThisIsMyPC Ring 0 driver via its Input/Output Control (IOCTL) interface.^1^ The attacker will attempt to supply malformed bytecode payloads to the PawnPP interpreter or exploit buffer overflows in the IOCTL dispatch routines to achieve arbitrary read/write primitives within kernel memory.^6^ Furthermore, an elevated attacker will target the driver's state-enforcement callbacks, attempting to dynamically alter the list of protected registry keys to shield their own malicious persistence mechanisms from detection and remediation by native Endpoint Detection and Response (EDR) solutions.^1^

In scenarios involving local physical access, the threat model expands to encompass hardware-based attacks targeting the system's memory and boot chain. Attackers may introduce malicious peripherals via PCIe, Thunderbolt, or USB4 interfaces to execute Direct Memory Access (DMA) attacks, attempting to read or modify physical memory before the operating system fully initializes.^1^ While the primary mitigation for this vector is the native Windows Kernel DMA Protection utilizing the Input-Output Memory Management Unit (IOMMU), the ThisIsMyPC kernel driver must ensure it strictly utilizes official DMA abstraction APIs, such as AllocateCommonBuffer, rather than manually constructing scatter-gather lists that could inadvertently expose physical memory pages to unauthorized hardware.^1^ Additionally, physical attackers may attempt to tamper with the system's Unified Extensible Firmware Interface (UEFI) variables to disable Secure Boot, allowing the loading of unsigned, malicious kernel modules that could entirely overwrite or bypass the ThisIsMyPC driver.^1^

### 2.1 The ASUS Armoury Crate and Razer Synapse Precedents

To fully comprehend the severity of the threat landscape facing hardware control utilities, it is imperative to analyze real-world exploitation incidents involving architecturally similar software. Utilities that bridge user-mode interfaces with kernel-level hardware execution are prime targets for adversaries because they often implement custom, flawed security boundaries rather than relying on native Windows access controls.

A highly illustrative example is the critical vulnerability discovered in the ASUS Armoury Crate software suite, tracked as CVE-2025-3464.^3^ Armoury Crate is a centralized application responsible for managing device configurations, firmware updates, and RGB illumination.^5^ To execute these functions, the user-mode application communicates with a virtual kernel driver, AsIO3.sys, which creates a device object named `\Device\Asusgio3`.^5^ To prevent unauthorized interaction with this highly privileged device, the driver implemented a custom authorization mechanism. It restricted handle acquisition to processes that matched a hardcoded SHA-256 hash corresponding to the legitimate AsusCertService.exe binary, or processes whose PIDs were explicitly added to an allowlist by that service.^5^

Security researchers identified that this architecture was fundamentally flawed due to a Time-of-Check to Time-of-Use (TOCTOU) race condition (CWE-367).^3^ An attacker operating with low-level, standard user privileges could bypass the driver's authorization by executing a hard link manipulation attack.^5^ The methodology involved the attacker creating a hard link, named core.exe, that pointed to an attacker-controlled malicious executable.^5^ The attacker launched this malicious payload and suspended its execution.^3^ Crucially, during this suspended state, the attacker deleted the core.exe hard link and immediately recreated it, this time pointing it to the legitimate, cryptographically signed AsusCertService.exe binary.^5^ When the AsIO3.sys kernel driver processed the subsequent IRP_MJ_CREATE request and queried the file system to calculate the SHA-256 hash of the calling process's backing executable, it read the newly linked, legitimate binary.^5^ The driver validated the hash, successfully authenticated the caller, and granted the suspended malicious process a handle to the `\Device\Asusgio3` interface.^5^ Because the driver's design lacked proper handle acquisition timestamp validation and relied on asynchronous userland file hash checks, the attacker achieved complete authorization bypass.^5^ Once the malicious process resumed execution, it utilized the compromised driver to map arbitrary physical memory addresses via ZwMapViewOfSection, communicate directly with raw I/O ports, and read or write values to Model-Specific Registers (MSRs), resulting in a total compromise of the operating system.^5^

Similarly, the Razer Synapse management software has a documented history of severe privilege escalation vulnerabilities stemming from improper service architecture and weak directory permissions. In the vulnerability tracked as CVE-2025-27811, a local privilege escalation defect was identified within the razer_elevation_service.exe component of Razer Synapse 4.^11^ This SYSTEM-level service improperly handled Inter-Process Communication, exposing a vulnerable Component Object Model (COM) interface.^12^ A local attacker with limited privileges could obtain a reference to this COM interface and craft specific requests that triggered the service to execute arbitrary operations with elevated privileges.^11^

An earlier vulnerability in the same software suite, CVE-2022-47631, highlighted the extreme danger of insecure installation paths.^14^ The Razer Synapse installer permitted an unprivileged user to create the `%PROGRAMDATA%\Razer` directory structure before the actual software installation occurred.^15^ The attacker could subsequently place a malicious, Trojan-horse Dynamic Link Library (DLL) into the `\Synapse3\Service\bin` directory and explicitly deny write access to the SYSTEM user.^14^ When the highly privileged Razer service subsequently initialized, it attempted to validate the DLLs in its directory.^14^ However, attackers exploited a race condition by replacing a valid, legitimate Razer DLL with the malicious payload immediately after the service completed its security check but before the library was mapped into memory.^14^ The service, running as NT AUTHORITY\SYSTEM, executed the attacker's DLL, granting immediate administrative privileges.^14^

These precedents unequivocally demonstrate that ThisIsMyPC cannot rely on PID allowlisting, user-space file hashing, or custom authorization loops to secure the boundary between the Session 1 GUI and the Session 0 SYSTEM service. Relying on the identity of a calling process is inherently volatile due to PID reuse, rapid process termination, and hard link manipulation.^1^ The architecture must demand that all service binaries and dependencies reside exclusively in locked, administrator-only directories (e.g., `C:\Program Files\`) to neutralize pre-execution DLL planting, and the IPC channels must be secured using cryptographic mutual authentication rather than environmental context checks.

## 3. Exploitation of the User-Mode to System Service Boundary: IPC Subversion

The fundamental requirement for ThisIsMyPC to persist user configurations and translate GUI interactions into hardware commands necessitates a robust Inter-Process Communication (IPC) channel between the medium-integrity desktop application and the highly privileged Session 0 service. Windows provides several native IPC mechanisms, including named pipes and Remote Procedure Calls (RPC). However, the implementation of these channels introduces profound security risks, primarily revolving around token impersonation, pipe squatting, and Man-in-the-Middle (MITM) relay attacks.

### 3.1 Named Pipe Client Impersonation and the SeImpersonatePrivilege

The most critical vulnerability associated with Windows named pipes is the abuse of client impersonation. By design, the Windows security model allows a server application to temporarily assume the security context -- and thereby the privileges -- of a client that authenticates to it.^16^ This capability is governed by the SeImpersonatePrivilege ("Impersonate a client after authentication"), a powerful user right assigned by default to the local Administrators group and critical system service accounts, including LOCAL SERVICE and NETWORK SERVICE.^17^ While impersonation is a legitimate feature intended to allow services to safely access resources on behalf of a requesting user (such as a print spooler writing a file to a user's directory), it provides a direct vector for privilege escalation if an attacker compromises a service account.^18^ If an adversary gains execution context within a process holding the SeImpersonatePrivilege, they can coerce a higher-privileged entity -- specifically the NT AUTHORITY\SYSTEM account -- into connecting to an attacker-controlled IPC mechanism, capturing the SYSTEM token, and elevating their own privileges.^18^

This specific attack methodology has been exhaustively documented and operationalized through a family of exploits colloquially known as "Potatoes," which includes RottenPotato, JuicyPotato, PrintSpoofer, RoguePotato, and GodPotato.^4^ The core execution flow across these variants relies on instantiating a malicious named pipe server and forcing a privileged Windows component to authenticate to it.^4^ In a typical PrintSpoofer attack, the adversary utilizes the CreateNamedPipe API to establish a pipe (e.g., `\\.\pipe\malicious_pipe`) and invokes ConnectNamedPipe to pause the thread and await a connection.^4^ The attacker then triggers a vulnerability or intended behavior in a privileged service to force a connection. PrintSpoofer, for instance, abuses the RpcRemoteFindFirstPrinterChangeNotificationEx API within the Print Spooler service, instructing the SYSTEM-level spooler to send notification events to the attacker's named pipe.^4^ Other variants, such as JuicyPotato and GodPotato, leverage Distributed Component Object Model (DCOM) activation and Object Exporter Identifier (OXID) resolution to trick the RPC subsystem into authenticating against a local, attacker-controlled proxy, which forwards the authentication to the named pipe.^4^

Once the SYSTEM service connects to the malicious pipe, the attacker's server must execute a specific sequence of Windows API calls to successfully steal the token. Crucially, the server must read at least one byte of data from the pipe using the ReadFile function.^4^ If the attacker attempts to impersonate the client without first reading data, the operation will fail, returning the ERROR_CANNOT_IMPERSONATE (1368) code.^4^ Following the successful read operation, the attacker calls ImpersonateNamedPipeClient, which instructs the operating system to swap the current thread's security token with the impersonation token of the connected SYSTEM client.^4^ At this juncture, the thread is operating under SYSTEM context, but to launch a persistent payload, the attacker must convert this temporary state into a primary process token.^16^ The attacker uses OpenThreadToken to retrieve a handle to the impersonation token and passes it to the DuplicateTokenEx API, specifying the TokenPrimary flag.^4^ Finally, the attacker invokes CreateProcessWithTokenW or CreateProcessAsUser, supplying the duplicated primary token and the path to their payload (e.g., cmd.exe or a reverse shell), effectively spawning a new, fully interactive process with unmitigated SYSTEM privileges.^4^

For ThisIsMyPC, the existence of this impersonation architecture mandates strict defensive configurations. If the Session 0 SYSTEM service initiates connections to clients without properly configuring its security boundaries, an attacker could set up a rogue pipe server and force the ThisIsMyPC service to connect to it, surrendering its SYSTEM token.

### 3.2 Named Pipe Squatting and Initialization Races

A distinct vulnerability targeting the initialization phase of SYSTEM services is the "named pipe squatting" attack.^8^ When a privileged service starts, it typically creates a named pipe with a statically defined string name to accept incoming commands. Because the Windows Object Manager allows processes to create objects within the `\Device\NamedPipe\` namespace, an unprivileged attacker can exploit the predictability of the service's pipe name by preemptively creating the pipe before the service initializes.^8^

This attack pattern was successfully weaponized against the Microsoft Sysinternals PsExec utility (CVE-2021-1733).^8^ When PsExec attempts to launch an executable on a remote machine, it extracts and executes a temporary service component, PSEXESVC.EXE, under the Local System account.^8^ This service creates a named pipe, predictably named `\PSEXESVC`, to receive execution instructions from the client.^21^ The service's code explicitly requested that the pipe be created with an Access Control List (ACL) that denied connection access to non-administrative users.^8^ However, an unprivileged local attacker could execute a malicious application that called CreateNamedPipe to instantiate the `\PSEXESVC` pipe before the legitimate PsExec service was triggered.^21^ The attacker created this pipe with a highly permissive Security Descriptor, granting full read/write access to standard users.^21^ When the legitimate SYSTEM-level PSEXESVC.EXE subsequently initialized and called CreateNamedPipe with the identical string name, the Windows Object Manager did not create a new pipe; instead, it merely returned a handle to the existing pipe created by the attacker.^21^ Crucially, the Object Manager ignored the restrictive ACL requested by the SYSTEM service and retained the permissive ACL applied by the attacker during the initial creation.^21^ Consequently, the unprivileged attacker could connect to the squatted pipe and issue arbitrary execution commands directly to the SYSTEM service, achieving complete local privilege escalation.^21^

This vulnerability highlights a critical failure in standard Security Descriptor Definition Language (SDDL) enforcement. If a pipe is squatted, the intended SDDL is completely bypassed.^21^ Therefore, the ThisIsMyPC Session 0 service must not rely solely on applying an SDDL string during pipe creation. It must explicitly pass the FILE_FLAG_FIRST_PIPE_INSTANCE flag within the CreateNamedPipe API call.^8^ This characteristic ensures that the operating system will definitively fail the creation request if a pipe with the specified name already exists within the namespace, immediately neutralizing any attempt by an unprivileged user to squat the communication channel.^8^

### 3.3 Man-in-the-Middle (MITM) and Relay Attacks via API Hooking

Even if the named pipe is successfully created by the SYSTEM service with a restrictive SDDL (e.g., limiting access exclusively to the Administrators group) and the FILE_FLAG_FIRST_PIPE_INSTANCE is utilized, the IPC channel remains vulnerable to advanced Man-in-the-Middle (MITM) and relay attacks. Adversaries recognize that relying on the operating system to validate the Process ID (PID) of the connecting client is an inherently fragile security control. Attackers deploy instrumentation tools, such as the pipetap proxy utility, to subvert hardened named pipes.^4^

Instead of attempting to connect directly to the restrictive pipe from an unauthorized process, the attacker injects a proxy Dynamic Link Library (DLL) directly into the memory space of the legitimate, authorized GUI client process.^4^ Once injected, this helper DLL utilizes inline API hooking (often via libraries like Microsoft Detours) to intercept calls to ReadFile and WriteFile specifically when the target handle corresponds to the named pipe.^4^ This methodology completely bypasses both SDDL enforcement and PID validation. Because the connection is initiated from within the trusted process, the operating system's GetNamedPipeClientProcessId check returns the legitimate PID, and the SDDL validation passes because the GUI process holds the requisite permissions.^4^ However, the injected proxy DLL allows the attacker to intercept, drop, modify, or replay the raw UTF-8, UTF-16, or hexadecimal payloads traversing the pipe before they are consumed by the SYSTEM service.^4^ The attacker can utilize this position to fuzz the IPC channel, hunting for deserialization vulnerabilities or unauthenticated command verbs within the SYSTEM service's parsing logic.^4^

### 3.4 Required IPC Mitigations for ThisIsMyPC

To establish a resilient architecture capable of defeating impersonation, squatting, and MITM attacks, ThisIsMyPC must implement a defense-in-depth IPC model that extends significantly beyond basic SDDL enforcement.

1. **Defeating Squatting:** As previously established, the Session 0 service must unconditionally use the FILE_FLAG_FIRST_PIPE_INSTANCE when instantiating its communication pipes to ensure it retains absolute control over the object's security descriptor.^8^

2. **Defeating Impersonation:** When the Session 1 GUI connects to the Session 0 service, it must explicitly restrict the impersonation level of its token. The client must open the pipe connection utilizing the SECURITY_SQOS_PRESENT and SECURITY_IDENTIFICATION flags.^4^ This configuration allows the SYSTEM service to verify the identity and access rights of the client (Identification) but strictly prohibits the service from utilizing the client's token to perform actions or spawn processes (Impersonation/Delegation).^4^ This adheres to the principle of least privilege and neutralizes the utility of the token if the service is compromised.

3. **Defeating MITM and Replay Attacks:** To prevent injected DLLs from manipulating payloads in transit, the IPC channel must implement cryptographic mutual authentication and data encryption.^22^ Standard named pipes transmit data in plaintext. ThisIsMyPC should upgrade the channel to utilize authenticated RPC over named pipes (ncacn_np), explicitly enforcing the RPC_C_AUTHN_LEVEL_PKT_PRIVACY authentication level.^22^ This configuration mandates the use of Kerberos or NTLMv2 to mutually authenticate both the client and the server via Service Principal Names (SPNs) before data exchange occurs.^22^ Furthermore, PKT_PRIVACY guarantees that every packet traversing the pipe is cryptographically signed for integrity and encrypted for confidentiality.^22^ To specifically defeat replay attacks, the protocol must incorporate connection nonces -- random, single-use cryptographic tokens generated during the initial handshake that must be validated with every subsequent configuration command.^23^

By implementing this comprehensive IPC hardening strategy, the architecture neutralizes the primary vectors through which user-mode attackers pivot into SYSTEM execution.

## 4. Kernel Driver Interfaces: IOCTL Abuse and Bytecode Verifier Failures

The boundary separating the Session 0 user-mode service and the Ring 0 PawnIO kernel driver represents the ultimate escalation path within the ThisIsMyPC architecture. To enact low-level hardware state changes -- such as polling embedded controllers for thermal data or manipulating SMBus/I2C registers for RGB lighting -- the user-mode components must communicate with the WDF kernel module via Input/Output Control (IOCTL) codes.^1^ The security of this interface is paramount. Vulnerabilities within the device initialization, the IOCTL dispatch routines, or the bytecode interpreter engine lead directly to arbitrary kernel memory corruption. Such flaws allow an attacker to bypass Hypervisor-Protected Code Integrity (HVCI), neutralize native EDR telemetry, and achieve absolute, persistent system compromise.^1^ Advanced threat actors actively hunt for signed, vulnerable drivers to facilitate Bring Your Own Vulnerable Driver (BYOVD) attacks, utilizing them as kernel-level execution proxies.^1^

### 4.1 Device Initialization and FILE_DEVICE_SECURE_OPEN Bypasses

The foundational defense mechanism for any WDM or WDF driver exposing a device interface to user-space is the secure initialization of its Device Object. When a driver calls the legacy IoCreateDevice API, the function does not permit the developer to specify an Access Control List (ACL) directly in the code; instead, it relies on external registry configurations or INF files, which are frequently omitted, leaving the device accessible to the Everyone group.^24^

To remediate this, Microsoft introduced the IoCreateDeviceSecure routine (and its wrapper WdmlibIoCreateDeviceSecure), which allows the developer to instantiate a named device object while explicitly defining its security descriptor using a Security Descriptor Definition Language (SDDL) string.^24^ A secure driver will utilize an SDDL string such as `D:P(A;;GA;;;SY)(A;;GA;;;BA)`, which strictly restricts handle acquisition to the NT AUTHORITY\SYSTEM account (SY) and the local Administrators group (BA).^24^

However, empirical vulnerability research reveals a catastrophic and frequently implemented bypass technique. If the developer utilizes IoCreateDeviceSecure to enforce a strong DACL but fails to apply the FILE_DEVICE_SECURE_OPEN characteristic flag in the DeviceCharacteristics parameter, the security boundaries are rendered entirely ineffective against namespace traversal.^24^ The Windows Object Manager dictates that every named device possesses its own hierarchical namespace.^24^ When a user-mode application calls the CreateFile API, the request is routed to the I/O Manager.^26^ If the application attempts to open the root device (e.g., `\Device\ThisIsMyPC`) and the user lacks the necessary privileges defined in the SDDL, the I/O Manager denies the request.^24^ However, if the FILE_DEVICE_SECURE_OPEN flag is omitted, the Object Manager's behavior changes dramatically when handling a path that extends beyond the device name.^24^ An unprivileged attacker can simply append an arbitrary string to the device path, requesting a handle to `\Device\ThisIsMyPC\BypassString`.^24^ The I/O Manager processes this request, identifies the root device object, but assumes the trailing string indicates the request is intended for a file system driver managing a directory structure.^24^ Crucially, the I/O Manager assumes the driver will handle the security evaluation for the trailing namespace and therefore does not apply the root device's SDDL ACL to the IRP_MJ_CREATE open request.^24^ The request is forwarded directly to the driver's dispatch routine. If the driver's DispatchCreate function is a simple stub that returns STATUS_SUCCESS without manually validating the security context of the extended path, the unprivileged attacker is granted a valid handle to the device.^24^ With this handle, the attacker can transmit arbitrary IOCTLs to the kernel driver, entirely bypassing the intended Administrator/SYSTEM restrictions.^24^

Therefore, it is an absolute architectural mandate that the ThisIsMyPC PawnIO kernel module unconditionally enforces both the restrictive SDDL string and the FILE_DEVICE_SECURE_OPEN characteristic during initialization.^1^

### 4.2 IOCTL Dispatch Vulnerabilities: Buffer Overflows and Type Confusion

Even when the device handle is securely restricted to administrative users, the driver's internal IOCTL handler (IRP_MJ_DEVICE_CONTROL) remains a prime target for exploitation. If an attacker has elevated to Administrator (or is operating within ThisIsMyPC's Owner Mode), they can interact with the IOCTLs. If the driver is poorly written, the attacker can use it as a BYOVD payload to attack the kernel itself, escalating from Administrator to SYSTEM or bypassing kernel-level mitigations.

A prominent example of IOCTL exploitation is the vulnerability within the Windows Ancillary Function Driver for WinSock (afd.sys), documented as CVE-2023-21768.^6^ The flaw resided within the driver's AfdNotifyRemoveIoCompletion function, which processed user-mode I/O operations.^6^ When processing an IOCTL, a secure driver must determine whether the request originated from user-mode or kernel-mode by checking the PreviousMode variable in the thread context.^6^ If the request comes from user-mode, the driver must invoke the ProbeForRead and ProbeForWrite APIs to ensure that any memory pointers provided within the IOCTL input structure actually point to valid user-space addresses, preventing the driver from inadvertently modifying critical kernel structures on the user's behalf.^1^ In CVE-2023-21768, the afd.sys driver contained a specific code path where the PreviousMode check and the subsequent ProbeForWrite validation were missing.^6^ An attacker could craft a malicious IOCTL containing an unknown structure where a specific field (e.g., field_0x18) was populated with a target kernel address.^6^ Because the driver failed to validate the boundary of the pointer, it blindly wrote data to the attacker-supplied kernel address, granting the attacker an arbitrary "Write-Where" primitive.^6^

Attackers typically weaponize this primitive by targeting the _EPROCESS structure of their own calling process.^6^ By calculating the offset to the Token field or the _SEP_TOKEN_PRIVILEGES structure, the attacker uses the vulnerable driver to flip the privilege bytes in kernel memory, manually enabling SeDebugPrivilege and SeLoadDriverPrivilege.^6^ This silently elevates the attacker's medium-integrity process to NT AUTHORITY\SYSTEM without triggering conventional UAC prompts or EDR alerts.^6^

To mitigate these attacks, the ThisIsMyPC driver must implement an absolute zero-trust model for all data crossing the Ring 0 boundary. The driver must define its IOCTLs using METHOD_BUFFERED, which forces the I/O Manager to allocate a system buffer in non-paged pool memory, copying the user's data into it safely before the driver accesses it.^1^ The driver must never use METHOD_NEITHER, which exposes raw user-space pointers directly to the kernel.^1^ Furthermore, the driver's dispatch routine must meticulously validate the InputBufferLength and OutputBufferLength of every IRP_MJ_DEVICE_CONTROL request against the expected size of the defined structures to prevent buffer overflows, and explicitly call ProbeForRead/ProbeForWrite on any embedded pointers.^1^

### 4.3 Kernel-Resident Bytecode Interpreters: PawnPP and eBPF Analogies

Beyond standard IOCTL dispatch flaws, the ThisIsMyPC architecture utilizes the PawnPP bytecode interpreter to execute hardware manipulation logic safely.^1^ Instead of exposing dangerous APIs like MmMapIoSpace (arbitrary physical memory mapping) or unconstrained IN/OUT port execution directly to user-space -- which are primary signatures for malware and trigger immediate HVCI violations -- PawnIO requires user-space to supply predefined bytecode modules.^1^ The kernel-resident PawnPP engine interprets this bytecode, allowing it to perform safety checks before interacting with the Hardware Abstraction Layer (HAL).^1^ While this architectural abstraction effectively neutralizes the hypervisor violations associated with legacy tools like WinRing0, running a complex bytecode interpreter directly within Ring 0 introduces profound systemic risks. If the interpreter engine contains logical flaws, an attacker supplying malformed bytecode can induce kernel crashes or execute arbitrary instructions.

The global IT outage triggered by the CrowdStrike Falcon EDR sensor in July 2024 provides a stark, catastrophic warning regarding in-kernel interpreters. The CrowdStrike CSagent.sys driver incorporated a kernel-mode content interpreter designed to evaluate dynamically fetched configuration templates (Channel File 291).^1^ The driver's compiled parser was rigidly hardcoded to expect exactly 20 input parameter fields within the data structure.^1^ When an automated update supplied a template containing 21 fields, the kernel interpreter attempted an out-of-bounds memory read.^1^ Because this violation occurred inside a highly privileged, boot-start Ring 0 driver, the resulting PAGE_FAULT_IN_NONPAGED_AREA exception went unhandled, triggering an infinite Blue Screen of Death (BSOD) boot loop across millions of systems.^1^

The PawnPP interpreter presents a parallel risk profile. We can analyze its required security posture by examining the Linux Extended Berkeley Packet Filter (eBPF) architecture, which similarly allows user-provided bytecode to execute within the kernel.^31^ The core of eBPF's security is its "Verifier," a static analysis engine that scrutinizes every bytecode program before execution.^9^ To prevent a user-supplied script from crashing the kernel or entering infinite loops, the eBPF verifier utilizes abstract interpretation to disassemble the bytecode and construct a Control Flow Graph (CFG).^9^ It ensures the CFG is a Directed Acyclic Graph (DAG) or contains strictly bounded, provably finite loops.^9^ Furthermore, the verifier aggressively tracks the state and type of all 11 virtual registers (e.g., ensuring a pointer is not added to another pointer) and strictly enforces memory bounds checking on every read/write operation to guarantee the bytecode cannot access memory outside its allocated 512-byte stack or specific context structures.^9^

For ThisIsMyPC to safely operate the PawnPP interpreter in the Windows kernel, it must adopt an equally rigorous, multi-staged verification architecture.

1. **User-Space Cryptographic Validation:** The Session 0 service must act as a primary gatekeeper. It must perform strict cryptographic verification of the bytecode payload, ensuring it is signed by the developer's private key, before ever transmitting the payload to the kernel via IOCTL.^1^ The kernel driver must reject any unsigned or tampered bytecode.

2. **Kernel-Mode Verifier:** Inside Ring 0, the PawnPP engine must implement a static analysis verifier akin to eBPF. It must validate all jump offsets to prevent execution outside the bytecode buffer, restrict loop iterations to prevent CPU exhaustion (Denial of Service), and strictly type-check all arguments passed to hardware helper functions.^9^

3. **Structured Exception Handling:** The interpreter's core execution loop must be wrapped in rigorous structured exception handling (`__try` / `__except` blocks).^1^ This ensures that if the verifier fails and a malformed byte sequence causes an out-of-bounds read or an invalid instruction fault, the exception is safely caught and handled, resulting in a graceful driver error rather than a catastrophic system-wide BSOD.^1^

## 5. Weaponization of State Enforcement Callbacks (CmRegisterCallbackEx)

To fulfill its primary directive of persisting user configuration preferences against automated OS reversions, ThisIsMyPC utilizes kernel callback frameworks, most notably CmRegisterCallbackEx, to actively filter and protect specific registry hives.^1^ This API enables a kernel driver to hook into the Windows Configuration Manager.^1^ When the driver registers its callback, the kernel creates a CM_CALLBACK_CONTEXT_BLOCK and inserts it into the globally maintained CmpCallBackVector doubly linked list.^33^ Once registered, whenever any thread on the system attempts to open, read, enumerate, or modify a registry key, the kernel synchronously triggers the callback, supplying a REG_XXX_KEY_INFORMATION structure that details the impending operation.^1^ The driver can inspect the desired access rights, modify the data in-flight, or completely block the operation by returning STATUS_ACCESS_DENIED.^1^ This mechanism is perfectly suited for ThisIsMyPC to lock down hardware configuration keys and prevent the Update Session Orchestrator (UsoClient.exe) from overwriting them.^1^

However, the CmRegisterCallbackEx framework is a dual-use technology that is extensively documented as a primary persistence mechanism for rootkits and Advanced Persistent Threats (APTs).^7^ Threat actors weaponize these exact callbacks to enforce the persistence of their malicious artifacts, rendering them completely invisible to or unremovable by user-space security tools.^7^

A prominent example is the operational tradecraft of the Chinese state-sponsored APT group Mustang Panda, which frequently utilizes custom kernel-mode rootkits derived from the open-source "Hidden" rootkit project.^7^ After establishing a foothold and escalating privileges, the APT deploys a driver that invokes InitializeRegistryFilter to register a CmRegisterCallbackEx routine.^34^ The threat actors configure this callback to monitor operations against critical persistence locations, such as the `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` hive or the `HKLM\System\CurrentControlSet\Services` hive where their malicious payload is registered.^7^ When an incident responder, an EDR agent, or a standard system utility (like regedit.exe) attempts to query the malicious key (REG_PRE_QUERY_VALUE_KEY), the rootkit intercepts the request and spoofs a STATUS_OBJECT_NAME_NOT_FOUND error, effectively blinding the security tool to the malware's existence.^36^ If an automated remediation script attempts to delete the key (REG_PRE_DELETE_KEY), the callback returns STATUS_ACCESS_DENIED, blocking the operation entirely.^1^

This presents a critical architectural risk for ThisIsMyPC. If the application's design allows the user-mode Session 0 service or the GUI to dynamically transmit a list of "protected keys" to the kernel driver via an IOCTL, the architecture becomes highly susceptible to subversion. If an elevated attacker compromises the Session 0 service or reverses the IPC protocol, they could send a malicious IOCTL instructing the ThisIsMyPC driver to protect the attacker's own malware registry keys.^1^ By feeding the driver a list containing their payload's Run key or EDR policy hives (e.g., `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender`), the attacker co-opts ThisIsMyPC's defensive callbacks, turning the legitimate hardware tool into an impenetrable, signed rootkit shield.^1^

To defend against the subversion and weaponization of the CmRegisterCallbackEx framework, the ThisIsMyPC architecture must implement strict, unalterable state locking.

1. **Eradicate Dynamic Target Lists:** The kernel driver must absolutely abandon any reliance on dynamic, unverified lists of protected registry keys supplied by user-space during runtime.^1^

2. **Cryptographic Sealing:** The list of registry keys eligible for protection must either be statically compiled within the EV-signed .sys binary itself, or it must be provided via a configuration file that requires strict cryptographic signature validation (using a hardcoded public key) within the kernel before it is parsed and accepted.^1^

3. **Process Identity Validation:** The registry callback handler must implement bipartite logic to evaluate the identity of the calling process before returning STATUS_ACCESS_DENIED. Drawing inspiration from Microsoft's native ucpd.sys (UserChoice Protection Driver), the ThisIsMyPC driver should use PsGetCurrentProcessId to resolve the caller's EPROCESS block.^1^ The callback should permit modifications only if the operation originates from the cryptographically verified PID of the legitimate ThisIsMyPC Session 0 service, blocking all other unauthorized tampering attempts without inadvertently shielding alien malware from EDR scrutiny.^1^

## 6. File System Defense: Minifilter Subversion and Reparse Point Abuse

If the ThisIsMyPC threat model expands to require the protection of specific configuration files or dependent DLLs on disk, it will necessitate the implementation of a File System Minifilter driver utilizing the FltRegisterFilter API.^1^ A minifilter attaches to the Windows file system stack and registers callbacks via the FLT_REGISTRATION structure for specific I/O operations, such as IRP_MJ_CREATE (file open/create) and IRP_MJ_WRITE.^1^ When a user or application attempts to access a protected file, the Filter Manager routes the request to the minifilter's pre-operation callback, allowing the driver to inspect the FLT_CALLBACK_DATA and block the operation if it originates from an untrusted source.^37^ However, file system filter drivers operate within a complex, highly layered environment that exposes them to unique attack vectors, specifically altitude manipulation, filter unload attacks, and NTFS reparse point abuse.

### 6.1 Altitude Manipulation and Unload Attacks

The Windows Filter Manager coordinates the execution order of multiple minifilters (e.g., antivirus, encryption, virtualization) using an "altitude" integer system.^37^ Minifilters registered with higher altitude numbers process I/O requests earlier in the stack during the pre-operation phase.^37^ This hierarchical design introduces the vulnerability of altitude manipulation.^38^ An attacker who has achieved administrative privileges can bypass the protective capabilities of the ThisIsMyPC minifilter by deploying a malicious, signed driver and deliberately registering it with an altitude higher than the ThisIsMyPC driver.^38^ When a malicious process attempts to overwrite a protected configuration file, the IRP_MJ_CREATE request is routed to the attacker's higher-altitude filter first. The malicious filter can intercept the request, manipulate the IRP status, and complete the operation by returning a success code.^37^ By completing the IRP at a higher altitude, the Filter Manager halts the downward traversal of the request, effectively bypassing the ThisIsMyPC filter entirely.^37^

Furthermore, attackers frequently target the persistence of minifilters directly. The Windows operating system provides a native utility, fltmc.exe (Filter Manager Control Program), which allows administrators to load, unload, and enumerate minifilters.^39^ Adversaries routinely execute `fltmc unload <FilterName>` to forcefully detach defensive drivers from the file system stack, terminating their protection dynamically.^39^

To mitigate these architectural attacks, the ThisIsMyPC minifilter must mirror the persistence design of highly aggressive enforcement drivers like ucpd.sys. During the initialization phase and the population of the FLT_REGISTRATION structure, the developer must explicitly omit the FilterUnloadCallback routine.^1^ By setting this callback pointer to NULL, the driver is registered as NOT_STOPPABLE.^1^ The Filter Manager will subsequently reject any attempt -- even those originating from NT AUTHORITY\SYSTEM via fltmc -- to dynamically unload the driver during runtime, ensuring continuous protection until the system reboots.^1^

### 6.2 Complex Input Subversion: Reparse Points and Symbolic Links

The most technically sophisticated attacks against minifilters exploit the complex input and path resolution mechanisms of the Windows file system, specifically targeting NTFS Reparse Points (which include symbolic links and directory junctions).^40^ Minifilters frequently perform security checks based on the file path provided in the IRP_MJ_CREATE request. However, if an attacker utilizes a reparse point, they can create a severe Time-of-Check to Time-of-Use (TOCTOU) race condition.^40^

A critical demonstration of this attack pattern is the Use-After-Free (UAF) vulnerability discovered in the native Windows Cloud Files Mini Filter Driver (cldflt.sys), tracked as CVE-2025-62221.^40^ The cldflt.sys driver, operating at Ring 0, processes complex structured inputs from userland, including placeholder metadata and reparse point data used for cloud storage synchronization.^40^ The vulnerability manifested because the minifilter performed short-lived, transient security checks on file metadata but failed to safely manage the lifecycle of the objects associated with these complex paths.^40^ An authorized local attacker orchestrated a race condition by manipulating an NTFS symbolic link.^40^ The attacker initiated an I/O operation against a path containing a symlink, forcing the minifilter to evaluate the path and allocate memory structures for the request.^40^ Between the time the filter checked the metadata and the time the kernel actually used the backing memory, the attacker flipped the target path of the reparse point.^40^ This state manipulation caused the driver to desynchronize, leading it to free a kernel object while retaining a stale pointer to it.^40^ In subsequent operations, the driver dereferenced this stale pointer.^40^ The attacker utilized heap spraying techniques to reallocate the freed memory pool with attacker-controlled data structures.^40^ When the kernel accessed the manipulated data, the attacker achieved arbitrary memory reads (to defeat KASLR) and arbitrary memory writes, enabling control flow hijacking and an immediate escalation to SYSTEM privileges.^40^

For ThisIsMyPC to implement a secure minifilter, it must actively anticipate path redirection and complex input manipulation. The filter's IRP_MJ_CREATE pre-operation callback must never render a security decision based solely on the initial, unresolved file name string provided in the FLT_CALLBACK_DATA structure. Attackers will utilize reparse points to spoof paths, making malicious directories appear as protected paths to trick the filter into allowing access, or vice versa.^41^ The driver must utilize the Filter Manager APIs (such as FltGetFileNameInformation) with the FLT_FILE_NAME_NORMALIZED and FLT_FILE_NAME_QUERY_DEFAULT flags to explicitly force the I/O Manager to resolve all symbolic links and junction points, evaluating only the final, canonical target path before authorizing the file operation. Furthermore, the driver must meticulously track object lifecycles across pre- and post-operation callbacks to prevent the UAF vulnerabilities demonstrated in the cldflt.sys exploitation.^40^

## 7. Synthesized Threat Mitigation Blueprint

The architectural resilience of ThisIsMyPC against local privilege escalation, Bring Your Own Vulnerable Driver (BYOVD) attacks, and IPC hijacking requires the implementation of an absolute zero-trust framework across all privilege boundaries. The reliance on legacy security paradigms -- such as PID validation, user-space file hashing, or implicit trust in user-mode inputs -- must be universally replaced by cryptographic enforcement, strict token evaluation, and rigorous bounds checking. Based on the forensic analysis of documented vulnerabilities in comparable software, the following architectural constraints must be implemented to secure the tool:

1. **IPC Hardening and Anti-Squatting:** The named pipe bridging the Session 1 GUI and the Session 0 SYSTEM service must be instantiated using the FILE_FLAG_FIRST_PIPE_INSTANCE API flag to definitively neutralize preemptive pipe squatting attacks (e.g., CVE-2021-1733).^8^

2. **Impersonation and MITM Defense:** To defeat SeImpersonatePrivilege token theft (the "Potato" exploits) and proxy DLL injection attacks (pipetap), the IPC channel must mandate Kerberos mutual authentication via Service Principal Names (SPNs) and enforce the RPC_C_AUTHN_LEVEL_PKT_PRIVACY level for encrypted, signed payloads.^4^ The Session 0 service must require connecting clients to authenticate with the SECURITY_IDENTIFICATION flag, strictly prohibiting the service from fully impersonating the client.^4^

3. **Kernel Interface Restriction:** The PawnIO driver must strictly enforce the FILE_DEVICE_SECURE_OPEN characteristic during IoCreateDeviceSecure initialization. Omission of this flag allows attackers to append trailing strings to the device path, bypassing the Object Manager's SDDL evaluation and achieving unauthorized IOCTL access.^24^

4. **Bytecode Verifier Sandboxing:** Drawing lessons from the CrowdStrike BSOD and eBPF architectures, the PawnPP interpreter must never parse unverified dynamic payloads in Ring 0.^1^ All bytecode must be cryptographically signed, and the kernel engine must utilize static analysis (bounding loops, type-checking registers) and structured exception handling (`__try/__except`) to prevent malformed instructions from causing out-of-bounds reads or system crashes.^1^

5. **Callback Cryptographic Sealing:** The target lists utilized by state-enforcement callbacks (CmRegisterCallbackEx and FltRegisterFilter) must be cryptographically sealed. To prevent attackers from weaponizing these callbacks to shield malware or rootkit persistence keys, the driver must never accept dynamic exclusion lists from user-space without absolute signature verification.^1^ Additionally, the file system minifilter must fully resolve all NTFS reparse points before rendering access decisions to neutralize TOCTOU UAF attacks (e.g., CVE-2025-62221).^40^

By enforcing these rigorous architectural constraints, ThisIsMyPC can successfully manage low-level hardware abstraction and securely persist user configurations without inadvertently introducing catastrophic local escalation primitives into the modern Windows 11 kernel ecosystem.
